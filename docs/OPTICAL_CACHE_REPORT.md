# 五层光学磁盘缓存开发检查点 · 0.1.72.3

本次继续完整移植，补齐PhotoStore.swift中PhotoPreviewDiskCache的source/lit/dark/flare/boosted五层持久化。0.1.72.3仍为开发中的源码检查点，dist中的已交付安装包和便携包仍为0.1.72.2；不能将新源码测试结果套用到旧包。

## 实现

- Core/Imaging/OpticalLayerCache写入单个Brotli容器，五层一起原子替换；固定头、请求身份、宽高和每层SHA256验证防止半份缓存或静默像素损坏被接受。
- 身份包含解码源的路径/长度/修改时间/预览级别、实际光学栅格尺寸及配方版本。当前配方明确为sRGB BGRA8和用户要求的0%关灯基准，未来P3算法必须更新配方。
- 独立cache/optical-v1目录；750MiB及48项LRU上限，保留刚完成项；不触碰布局、缩略图或源图。写入失败仍返回已生成的图像。
- 相同冷请求合并，两路后台构建；GPU上传、离屏生成、读回和压缩在后台工作，发布时再次检查设备代次。每个设备的不可变色表由带引用计数的租约复用，最后一个构建结束后释放。
- 台面和幻灯均走异步光学工厂。GPU实例只保留元数据，不保留五层CPU数组。临时效果图在烘焙后立即释放；默认100%稳态直接复用lit，避免再为每片创建同值的第六张纹理。
- 渲染中的尺寸、宽高比和备用GPU图查询改为索引，避免逐片重复扫描全图库；加载占位文字复用格式，小到无法阅读时只显示片面。

Win2D允许从任意线程调用API，但跨线程资源必须保持正确所有权；参见[CanvasDevice.Lock说明](https://microsoft.github.io/Win2D/WinUI2/html/M_Microsoft_Graphics_Canvas_CanvasDevice_Lock.htm)。本实现只在后台操作构建私有的图和目标，UI发布前拒绝旧设备代次的结果。

## 性能发现及未闭合事项

新增缓存后的四规模短测确实导入10/100/500/1000张，但初版1000张CPU Draw P95约342ms，发现性能问题，未据绿色功能检查发布新包。加入分阶段Draw记录后，确认加载阶段反复遍历宽高比、备用图和图库，并有动态光照逐片调用及稳态首次烘焙开销。首轮、资源释放修复、查询索引修复与最终检查点分别保存，不能只保留较快结果。

最终源码检查点1000张进程退出0。整体Draw CPU P95为94.19ms；分阶段P95：加载92.46ms、平移3.19ms、点灯112.65ms、凑近43.26ms。导入6137ms、平铺及GPU准备8060ms；私有内存采样峰值818.71MiB。相比初版342ms有改进，但大图库加载、点灯仍明显不够流畅。这些是CPU回调而非GPU呈现数据。

0.1.72.2将应用动画与系统动画开关解耦，因此过去系统动画关闭时的低Draw P95不能直接作为当前完整两秒点灯的可比基线。当前仍需优化大图库加载和点灯，不声称60FPS或完整GPU呈现达标。

仍需继续：

2. 验证真正跨进程冷/热启动及1000张的热缓存行为；48项策略对小栅格大图库的命中率仍需权衡，不能仅凭单片热命中宣称全图库加速。
3. 异常退出留下的临时文件回收、长时间及磁盘耗尽行为尚未完整验收。
4. 新索引/默认lit复用后的最终四规模回归和便携/安装打包仍待执行。现有包保持0.1.72.2。
5. Display P3/线性光工作链仍未实现，五层缓存不代表色彩等价已完成。

完整移植目标仍未完成。本检查点证据见docs/evidence/optical-cache-*；后续以PROGRESS记录继续开发。
