# LightTable for Windows — 完整跨平台移植开发指令

## 一、你的身份与任务

你是一名具备高级工程能力的 Windows 桌面应用架构师、跨平台软件移植工程师、GPU 图像渲染工程师、UI/UX 工程师及自动化测试工程师。

现在需要你独立完成一项完整的软件移植工程。

**原项目：**

https://github.com/fuyuan9972-svg/LightTable

**项目名称：**

LightTable for Windows（观片台 Windows 版）

**源项目技术：**

Swift、SwiftUI、AppKit、Core Image、Metal、Sparkle。

**目标平台：**

Windows 11 x64，优先支持 Windows 11 23H2 及更新版本，并在技术允许的情况下兼容 Windows 10。

**最高目标：**

将原本只能在 macOS 运行的 LightTable 完整移植为 Windows 原生桌面应用。

这不是简单地模仿界面，也不是创建一个新照片浏览器，而是以原项目的完整源代码为依据，在 Windows 上重现全部功能、操作逻辑、视觉表现、动画、光学效果、声音、性能优化及数据保存能力。

### 不可妥协的基本原则

1. 所有原版功能必须保留。
2. 不允许为了简化开发而删除功能。
3. 不允许使用静态演示界面冒充真实功能。
4. 不允许用网页套壳代替高性能原生程序。
5. 不允许将专业灯箱交互降级为普通图片查看器。
6. 所有按钮、菜单、快捷键及操作都必须实际生效。
7. 保留原版的 UI 设计语言及布局比例。
8. 保留胶片灯箱的光学效果及交互体验。
9. 必须具备可靠的照片导入、缓存、预览和保存机制。
10. 最终必须可以在 Windows 上真正安装、运行和使用。
11. 所有功能必须经过实际验证，不得虚构测试结果。
12. 在开发中遇到技术困难，应优先寻找等价方案，而不是删减原有功能。
13. 不需要添加个人开发者署名、水印、特别鸣谢或个人品牌。
14. 保留原项目许可协议依法要求的原作者版权信息和第三方许可声明。
15. 不得破坏原项目的 macOS 代码。

## 四、第三阶段：完整移植照片管理系统

### 4.1 照片导入

支持：

- 单张照片导入
- 多张照片导入
- 完整文件夹导入
- 文件夹递归读取
- 文件和文件夹拖放
- 中文文件路径
- Unicode 文件名
- 长文件路径
- 重复图片识别
- 错误文件处理
- 文件不存在时的友好提示

图像格式应尽可能匹配原版 macOS 的实际支持范围。

至少保证常见 JPEG、PNG、TIFF、BMP 等格式。

HEIC、WebP、RAW 等格式应检查 Windows 系统编解码器和可用扩展，按兼容性测试结果实现。

不允许未经测试就声称支持所有 RAW 格式。

### 4.2 数据安全

必须确保：

- 不修改原始照片。
- 不覆盖原文件。
- 不重新压缩原图。
- 不擅自删除原图。
- 删除台面照片不等于删除磁盘文件。
- 所有照片默认只在本地处理。
- 任何错误操作不能导致原始文件丢失。

所有临时文件、布局文件和缓存文件必须与用户原图分离。

## 五、第四阶段：胶片灯箱系统

这是整个应用最核心的部分。

要求最大程度还原原版视觉效果及交互行为。

### 5.1 自由摆片

实现：

1. 将底栏照片拖动到台面。
2. 自由改变照片位置。
3. 自由旋转照片。
4. 调整单张照片大小。
5. 将照片移动到最上层。
6. 多张照片重叠显示。
7. 整体灯箱视野平移。
8. 整体缩放。
9. 单击选择照片。
10. Ctrl 多选。
11. Shift 框选。
12. Delete 批量移出台面。
13. 保留原版一键平铺功能。
14. 恢复整体视图。
15. 保存每张照片的位置、比例、角度和层级顺序。

一键平铺必须遵循原版布局替换语义，清除当前散片摆放并重新排列，而不是删除图库照片。

### 5.2 胶片外观

必须保留：

- 无多余边框的照片外观
- 轻微厚度效果
- 细薄侧沿
- 接触阴影
- 层级关系
- 拖动时自然的视觉反馈
- 选中时的状态反馈

特别要求：

普通拖动时不允许突然闪现蓝色边框。

只有主动选中、多选或框选时才显示必要的选择反馈。

### 5.3 灯箱光照

必须完整移植：

- 开灯
- 关灯
- 亮度调节
- 暗态胶片外观
- 透射光效果
- 局部高亮区域的光学表现
- 开灯瞬间的短暂过曝
- 随后亮度自然回落
- 多照片之间一致的灯光状态

参考原版 PhotoStore、PhotoOptics、OpticalDisplay 和 LightResponse 的实际算法。

必须分析其中的颜色矩阵、混合逻辑、亮度变化、模糊范围和缓存设计。

如 Direct2D 无法直接提供等价实现，应组合 Pixel Shader、Win2D 特效和颜色处理实现。

不得简单使用一张半透明白色图片覆盖整个画面来冒充透射光效果。

### 5.4 GPU 优化

要求：

- 优先通过 GPU 实现台面渲染。
- 避免每帧重新解码原图。
- 避免拖动时重复创建纹理。
- 复用静态胶片材质。
- 减少逐帧模糊。
- 降低内存分配压力。
- 使用合理的局部重绘策略。
- 保证持续操作期间画面稳定。
- 正确处理 GPU 设备丢失和显示器切换。

- 松开 Space 恢复。

- 台面布局

### 9.2 文件存储

使用 Windows 标准用户数据目录。

建议：

`%LOCALAPPDATA%\\LightTable\\`

需要正确区分：

- 用户配置
- 布局数据
- 图片缓存
- 日志

重新打开软件时：

1. 读取已保存布局。
2. 验证照片路径。

4. 准备对应图片预览。
5. 恢复台面视图。
6. 进入可操作界面。

文件缺失或损坏时必须友好处理。

不能因为一张照片加载失败就导致全部布局丢失。

## 十、第九阶段：图片缓存和性能优化

原版 v0.1.72 已经包含按显示尺寸动态加载图片的机制。

必须保留这一设计。

### 10.1 预览分级

参考原版：

- 256px
- 384px
- 512px
- 768px
- 1024px
- 1536px
- 2200px

根据实际显示大小和 DPI 选择合适预览尺寸。

### 10.2 动态缩放

要求：

- 连续缩放时保留已有预览。
- 停止缩放约 120ms 后按需升级预览。
- 相同尺寸请求合并。
- 迟到的低分辨率结果不能覆盖已显示的高清版本。
- 图片加载和解码不得阻塞 UI 主线程。
- 避免频繁重复生成纹理。

### 10.3 缓存设计

实现：

- 内存缓存
- 磁盘缓存
- LRU 或其他合理淘汰机制
- 请求去重
- 并发数量限制
- 内存预算
- GPU 纹理资源释放
- 缓存错误恢复
- 缩略图独立管理

### 10.4 启动准备卡片

完整保留原版启动准备流程。

尤其是：

- 唤醒观片台
- 恢复照片摆放
- 准备灯箱
- 准备高清照片
- 显示处理照片数量
- 出错重试
- 先查看可用照片

应按照实际任务进度驱动，而不是显示假的固定百分比。

空台面应能直接进入。

- 只有 UI，没有逻辑。
- 只有按钮，没有操作。

- 使用硬编码示例照片代替真正的文件导入。

**规则 6：保留测试证据**

记录真实编译命令、运行日志和测试结果。

**规则 7：处理技术阻塞**
